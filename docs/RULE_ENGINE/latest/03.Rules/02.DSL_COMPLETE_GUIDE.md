# 🔥 SIEM Rule DSL - Complete Reference

## Overview

This is a **pure DSL-based rule engine** where ALL rule logic is expressed in `.dsl` files. No JSON, no YAML, no hardcoded Rust conditions.

## Architecture

```
rules/siem_rules.dsl
        ↓
    DSL Parser (dsl_parser.rs)
        ↓
    AST Generation
        ↓
    Rule Compiler (dsl_executor.rs)
        ↓
    HashMap<log_type, Vec<CompiledRule>>  ← O(1) lookup
        ↓
    Event Evaluation (O(1) rule selection)
```

## Key Features

✅ **O(1) Rule Lookup**: Rules indexed by vendor:product  
✅ **Parent-Child Hierarchy**: Wazuh-style cascading rules  
✅ **No Runtime Parsing**: DSL compiled once at startup  
✅ **Regex Compiled Once**: Cached in HashMap  
✅ **10K+ EPS Ready**: No O(N) loops in hot path  
✅ **Runtime Reloadable**: Send SIGHUP to reload .dsl files

## DSL Syntax Reference

### Basic Rule Structure

```
RULE <rule_id>
[PARENT <parent_rule_id>]
WHEN
  <condition_expression>
[AGGREGATE count >= N within Ns]
[CORRELATE by field1, field2 count >= N within Ns]
THEN
  severity = <0-10>
  noalert = <0|1>
  tags = ["tag1", "tag2", ...]
  [enrich { key = "value", ... }]
END
```

### Boolean Operators

```
AND  - Logical AND
OR   - Logical OR
NOT  - Logical NOT
()   - Grouping
```

**Example:**

```
WHEN
  (event.vendor == "sophos" AND event.action == "deny")
  OR
  (event.vendor == "fortinet" AND bytes > 1000000)
```

### Comparison Operators

```
==   Equal
!=   Not equal
>    Greater than
<    Less than
>=   Greater than or equal
<=   Less than or equal
```

**Example:**

```
WHEN
  event.severity >= 7
  AND bytes > 10000000
```

### Set Operations

```
IN      - Field value in set
NOT IN  - Field value not in set (NOT YET IMPLEMENTED)
```

**Example:**

```
WHEN
  dst.port IN [22, 23, 3389]
  AND user.name IN ["admin", "root"]
```

### String Operations

```
contains     - Substring search
starts_with  - Prefix match
ends_with    - Suffix match
matches      - Regex match
```

**Example:**

```
WHEN
  url.path contains "' OR 1=1"
  OR user_agent starts_with "sqlmap"
  OR message matches /Failed password for .* from [\d.]+/
```

## Rule Types

### 1. Basic Rules

Simple condition → action.

```
RULE SOPHOS_XGS_DENY
WHEN
  event.vendor == "sophos"
  AND event.product == "xgs"
  AND event.action == "deny"
THEN
  severity = 4
  noalert = 0
  tags = ["firewall", "sophos", "deny"]
END
```

**Execution**: O(1) lookup via `rules_by_log_type["sophos:xgs"]`

---

### 2. Parent-Child Rules (Hierarchical)

Child rules **only execute if parent matched**.

**Parent Rule:**

```
RULE SOPHOS_AUTH_FAIL
WHEN
  event.vendor == "sophos"
  AND event.category == "authentication"
  AND event.outcome == "failure"
THEN
  severity = 4
  noalert = 0
  tags = ["auth", "failure"]
END
```

**Child Rule:**

```
RULE SOPHOS_AUTH_FAIL_ADMIN
PARENT SOPHOS_AUTH_FAIL
WHEN
  user.name IN ["admin", "root", "administrator"]
THEN
  severity = 7  # Override parent severity
  noalert = 0
  tags = ["auth", "failure", "privileged_account"]
END
```

**Execution Flow:**

1. Evaluate `SOPHOS_AUTH_FAIL` against event
2. If matched → generate alert + store in `matched_rules`
3. Check if rule has children via `child_rules["SOPHOS_AUTH_FAIL"]`
4. Evaluate child `SOPHOS_AUTH_FAIL_ADMIN`
5. If child matches → generate alert with severity=7

**Performance**: Children only evaluated if parent matched (early exit)

---

### 3. Aggregation Rules

Trigger when rule matches N times within time window.

```
RULE SOPHOS_AUTH_BURST
WHEN
  RULE_MATCHED("SOPHOS_AUTH_FAIL")
AGGREGATE
  count >= 5
  within 60s
THEN
  severity = 7
  noalert = 0
  tags = ["auth", "burst", "anomaly"]
END
```

**Execution Flow:**

1. Each time `SOPHOS_AUTH_FAIL` matches → increment Redis counter
2. Key: `agg:SOPHOS_AUTH_BURST:client_id`
3. Expiry: 60 seconds
4. When count >= 5 → trigger alert

**Redis Commands:**

```
INCR agg:SOPHOS_AUTH_BURST:client1
EXPIRE agg:SOPHOS_AUTH_BURST:client1 60
GET agg:SOPHOS_AUTH_BURST:client1
```

---

### 4. Correlation Rules

Trigger when rule matches N times **for the same field values**.

```
RULE SOPHOS_BRUTE_FORCE
WHEN
  RULE_MATCHED("SOPHOS_AUTH_FAIL")
CORRELATE
  by client_id, user.name, src.ip
  count >= 5
  within 120s
THEN
  severity = 8
  noalert = 0
  tags = ["brute_force", "credential_attack"]
END
```

**Execution Flow:**

1. Each `SOPHOS_AUTH_FAIL` match → extract correlation fields
2. Key: `corr:SOPHOS_BRUTE_FORCE:client1:admin:192.168.1.50`
3. Increment counter in Redis
4. When count >= 5 for **same (client_id, user.name, src.ip)** → alert

**vs Aggregation:**

- **Aggregation**: Total count across all events
- **Correlation**: Count grouped by specific field values

**Example Scenario:**

```
Event 1: user=admin, src=192.168.1.50  → corr:...:admin:192.168.1.50 = 1
Event 2: user=admin, src=192.168.1.50  → corr:...:admin:192.168.1.50 = 2
Event 3: user=bob,   src=192.168.1.51  → corr:...:bob:192.168.1.51 = 1
Event 4: user=admin, src=192.168.1.50  → corr:...:admin:192.168.1.50 = 3
Event 5: user=admin, src=192.168.1.50  → corr:...:admin:192.168.1.50 = 4
Event 6: user=admin, src=192.168.1.50  → corr:...:admin:192.168.1.50 = 5 → ALERT!
```

---

### 5. Cross-Correlation Rules (Multi-Rule)

**NOT YET IMPLEMENTED** - Future feature

Trigger when **multiple different rules** match within time window.

```
RULE LATERAL_MOVEMENT_DETECTION
WHEN
  RULE_MATCHED("SOPHOS_AUTH_FAIL")
  AND RULE_MATCHED("WINDOWS_LOGIN_SUCCESS")
WITHIN 300s
THEN
  severity = 9
  noalert = 0
  tags = ["lateral_movement", "apt", "critical"]
END
```

**Execution Flow:**

1. Track all rule matches in Redis sorted set
2. Key: `xcorr:client1` → ZADD (timestamp, rule_id)
3. On each match → check if other required rules present in window
4. If all conditions met → trigger alert

## THEN Clause (Actions)

### Severity Levels

```
severity = 1   # Informational
severity = 2   # Low
severity = 4   # Medium
severity = 5   # Medium-High
severity = 6   # High
severity = 7   # High-Critical
severity = 8   # Critical
severity = 9   # Critical-APT
severity = 10  # Emergency
```

### Alert Suppression

```
noalert = 0   # Generate alert (default)
noalert = 1   # Silent - don't alert
```

**Use Case**: Track successful logins (for correlation) without alerting.

```
RULE WINDOWS_LOGIN_SUCCESS
WHEN
  event.code == "4624"
THEN
  severity = 2
  noalert = 1  # Don't alert on success
  tags = ["windows", "auth", "success"]
END
```

### Tags

```
tags = ["firewall", "sophos", "deny", "high_risk"]
```

Tags used for:

- Alert categorization
- MITRE ATT&CK mapping
- Dashboard filtering

### Enrichment (Optional)

```
enrich {
  mitre_technique = "T1021"
  tactic = "lateral_movement"
  risk_score = "85"
  priority = "high"
}
```

Adds extra fields to generated alert.

## Performance Characteristics

### O(1) Rule Lookup

**Before (O(N×M)):**

```rust
for event in events {
    for rule in &rules {  // ❌ 10K EPS × 50 rules = 500K iterations/sec
        if rule.log_types.contains(&event.log_type) {
            evaluate(rule, event);
        }
    }
}
```

**After (O(1)):**

```rust
for event in events {
    let log_type = format!("{}:{}", event.vendor, event.product);
    let rules = rules_by_log_type.get(&log_type);  // ✅ O(1) HashMap lookup

    for rule in rules {  // Only 5-10 rules per log_type
        evaluate(rule, event);
    }
}
```

**Performance Gain**: 500K iterations → 50K iterations (10× reduction)

### Regex Compilation

Regex patterns compiled **once at startup**, cached in HashMap.

```rust
pub struct RuleEngine {
    regex_cache: HashMap<String, Regex>,
}

fn get_or_compile_regex(&mut self, pattern: &str) -> Regex {
    self.regex_cache.entry(pattern).or_insert_with(|| {
        Regex::new(pattern).unwrap()
    }).clone()
}
```

**Before:** Regex compiled on every evaluation (slow)  
**After:** Regex compiled once, reused (fast)

## Usage

### Load Rules at Startup

```rust
use security_rule_engine::dsl_loader::load_dsl_rules_from_directory;

#[tokio::main]
async fn main() {
    // Load all .dsl files from rules/ directory
    let mut rule_engine = load_dsl_rules_from_directory("./rules")
        .expect("Failed to load DSL rules");

    println!("✅ Loaded {} rules", rule_engine.rules_count());
}
```

### Evaluate Event

```rust
use serde_json::json;

let event = json!({
    "event": {
        "vendor": "sophos",
        "product": "xgs",
        "action": "deny"
    },
    "src": { "ip": "192.168.1.50" },
    "dst": { "ip": "8.8.8.8", "port": 443 },
    "bytes": 12345
});

let log_type = "sophos:xgs";
let matches = rule_engine.evaluate(&event, log_type);

for m in matches {
    if !m.noalert {
        println!("🚨 Alert: {} (severity={})", m.rule_id, m.severity);
    }
}
```

## Troubleshooting

### Rule Not Matching

**Check:**

1. Log type indexing: `"sophos:xgs"` vs `"sophos:*"`
2. Field names: `event.vendor` vs `vendor`
3. Boolean logic: Ensure parentheses correct

**Debug:**

```rust
println!("Log type: {}", log_type);
println!("Candidate rules: {:?}", engine.get_rules_for_log_type(log_type));
```

### Parse Errors

```
Error: Expected '=', got Identifier("=")
```

**Fix:** DSL uses `=` for assignment, `==` for comparison

```
THEN
  severity = 5  ✅
  severity == 5 ❌
```

### Performance Issues

**Symptom:** High CPU at 10K EPS

**Check:**

1. Rule indexing: `rules_by_log_type` should have <10 rules per key
2. Regex compilation: Check `regex_cache` size
3. Child rule depth: Avoid deep hierarchies (>3 levels)

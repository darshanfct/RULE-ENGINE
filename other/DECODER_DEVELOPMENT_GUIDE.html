Decoder JSON Schema (v2)

Minimal Required Fields

{
    "schema_version": 2,
    "vendor": "vendor_name",
    "product": "product_name",
    "format": "kv_direct",
    "detect": { ... },
    "parsing": { ... }
}

Complete Schema Reference

{
    "schema_version": 2,
    "vendor": "string (required) - vendor identifier (lowercase)",
    "product": "string (required) - product identifier", 
    "format": "kv_direct | regex | json | syslog",
    "detect": {
        "contains": ["array of strings that MUST be present in log"],
        "not_contains": ["array of strings that MUST NOT be present (optional)"],
        "regex": "optional regex pattern for more precise matching",
        "priority": "integer (higher = checked first, default: 0)"
    },
    "parsing": {
        "kv_format": {
            "pair_delimiter": " (space between key=value pairs)",
            "kv_delimiter": "= (between key and value)"
        },
        "patterns": [
            {
                "name": "pattern_name",
                "regex": "regex with named groups (?P<name>...). Use (?P<kv_data>...) to capture the KV portion",
                "event_type": "firewall | endpoint | network | auth | etc"
            }
        ]
        // NOTE: For kv_direct format, patterns run FIRST to extract syslog headers,
        // then the kv_data capture is parsed as key-value pairs.
        // All fields are merged together.
    },
    "normalize": {
        "name": "optional product name override",
        "action": {
            "from_event": {
                "EventType1": "normalized_action1",
                "EventType2": "normalized_action2"
            }
        },
        "status": {
            "from_event": {
                "EventType1": "success",
                "EventType2": "blocked"
            }
        }
    },
    "severity_mapping": {
        "regex": {
            "severity=\"Critical\"": "critical",
            "severity=\"Warning\"": "medium",
            "default_pattern": "info"
        }
    }
}

Step-by-Step: Creating a New Decoder

Step 1: Identify the Log Format

Collect sample logs and identify:

  1. Unique identifiers - strings that appear ONLY in this vendor's logs
  2. Key-value format - what separates pairs? what separates key from value?
  3. Field names - what does the vendor call their fields?

Example Fortigate log:

date=2019-05-10 time=11:37:47 logid="0000000013" type="traffic" srcip=10.1.100.11 dstip=23.59.154.35 dstport=80 action="close"

Analysis:

  • Unique identifiers: logid=", type="traffic", etc.
  • KV format: space-separated pairs, = delimiter
  • Fields: srcip, dstip, dstport, action

Step 2: Create the Decoder JSON File

Create a new file in: logtest/decoders/vendors/{vendor}/{product}.json

{
    "schema_version": 2,
    "vendor": "fortinet",
    "product": "fortigate",
    "format": "kv_direct",
    "detect": {
        "contains": [
            "logid=\"",
            "devname="
        ],
        "priority": 10
    },
    "parsing": {
        "kv_format": {
            "pair_delimiter": " ",
            "kv_delimiter": "="
        },
        "patterns": [
            {
                "name": "fortigate_traffic",
                "regex": "^(?P<kv_data>.*)",
                "event_type": "firewall"
            }
        ]
    },
    "normalize": {
        "name": "fortinet-fw-ng",
        "action": {
            "from_event": {
                "accept": "allow",
                "deny": "deny",
                "close": "close",
                "drop": "drop"
            }
        }
    }
}

Step 3: No Manual Field Mapping Required!

With schema_version 2, field mapping is automatic via the PHF (Perfect Hash Function) global table.

The system automatically maps common vendor field names:

Vendor Field → Unified Schema Field
srcip → src_ip
dstip → dst_ip
srcport → src_port
dstport → dst_port
user → user
action → action
...and 200+ more mappings

See src/unified_field_map.rs for the complete mapping table.

Step 3b: Extracting Syslog Headers (Optional)

For logs with syslog prefixes (timestamp, hostname, gateway), use a pattern with named captures:

"parsing": {
    "kv_format": {
        "pair_delimiter": " ",
        "kv_delimiter": "="
    },
    "patterns": [
        {
            "name": "sophos_firewall_syslog",
            "regex": "^(?P<syslog_timestamp>\\d{4}-\\d{2}-\\d{2}T[\\d:.+]+)\\s+(?P<gateway>\\S+)\\s+(?P<kv_data>.*)",
            "event_type": "firewall"
        }
    ]
}

How it works for kv_direct format:

  1. Pattern regex runs first → extracts syslog_timestamp, gateway, and kv_data
  2. KV parser processes the kv_data portion → extracts device_name, src_ip, etc.
  3. All fields are merged together

Example:

Input:  "2025-12-03T11:14:34+05:30 _gateway device_name="SFW" src_ip="10.1.1.1""

After pattern:
  syslog_timestamp = "2025-12-03T11:14:34+05:30"
  gateway = "_gateway"
  kv_data = "device_name=\"SFW\" src_ip=\"10.1.1.1\""

After KV parse (on kv_data):
  device_name = "SFW"
  src_ip = "10.1.1.1"

Final merged result:
  syslog_timestamp = "2025-12-03T11:14:34+05:30"
  gateway = "_gateway"
  device_name = "SFW"
  src_ip = "10.1.1.1"

Step 4: Test Your Decoder

# From backend directory
./logtest/logtest-cli <<< 'date=2019-05-10 time=11:37:47 srcip=10.1.100.11 dstip=23.59.154.35'

Field Mapping: How It Works

The PHF (Perfect Hash Function) Advantage

Traditional approach (schema_version 1):

"map": {
    "srcip": "src_ip",
    "dstip": "dst_ip",
    "srcport": "src_port",
    ... (100+ lines per decoder!)
}

New approach (schema_version 2):

No "map" section needed - it's automatic!

How the Global Mapping Works

Raw Log: srcip=10.1.1.1 dstport=443 user=admin

    ┌─────────────────────────────────────────────────────────────────┐
    │                    UNIFIED_FIELD_MAP (PHF)                      │
    │  ┌─────────────────────────────────────────────────────────────┐│
    │  │ "srcip"    → "src_ip"                                       ││
    │  │ "dstport"  → "dst_port"                                     ││
    │  │ "user"     → "user"                                         ││
    │  │ ... 200+ vendor variations ...                              ││
    │  └─────────────────────────────────────────────────────────────┘│
    └─────────────────────────────────────────────────────────────────┘
                                  │
                                  v
    NormalizedEvent {
        src_ip: Some("10.1.1.1"),
        dst_port: Some(443),
        user: Some("admin"),
        ...
    }

Supported Field Categories

The unified mapping covers:

Category Example Raw Names Unified Name
Source IP srcip, source_ip, sip, clientip src_ip
Dest IP dstip, dest_ip, dip, destAddress dst_ip
Source Port srcport, sport, client_port src_port
Dest Port dstport, dport, destination_port dst_port
User user, username, user_name, acct user
Action action, Action, utm_action action
Protocol protocol, proto, Protocol protocol
Application app, application, appname application
File Path file_path, filepath, filePath file_path
Process process, process_name, proc process_name
Threat threat_name, threatname, virus threat_name

What If My Vendor Uses an Unmapped Field Name?

Two options:

Option A: Add to Global PHF (Recommended for common fields)

  1. Edit src/unified_field_map.rs
  2. Add your mapping to the UNIFIED_FIELD_MAP
  3. Rebuild the engine
// In unified_field_map.rs, add:
"my_vendor_srcip" => "src_ip",

Option B: Use Fallback to extracted_fields

  • Unmapped fields are automatically stored in extracted_fields HashMap
  • Rules can still reference them via the original field name

Testing Your Decoder

Using logtest-cli

# Single log test
./logtest/logtest-cli <<< 'your log here'

# From file
./logtest/logtest-cli -f sample_logs.txt

# Verbose output
./logtest/logtest-cli -v <<< 'your log here'

What to Verify

  1. Detection: Does the correct decoder get selected?

    [DEBUG] Decoded vendor: 'your_vendor', product: 'your_product'

  2. Field Extraction: Are all fields parsed?

    **Phase 2: Completed decoding.
src_ip: '10.1.1.1'
dst_port: '443'
user: 'admin'

  3. Unified Mapping: Are vendor fields mapped correctly?

    • srcip should appear as src_ip in output
    • dstport should appear as dst_port

  4. Rule Matching: Do your rules fire?

    **Phase 3: Completed filtering (rules).
id: '100001'
description: 'Your rule description'

Migration: From Schema v1 to v2

If you have existing decoders with explicit extract and map sections:

Before (v1):

{
    "schema_version": 1,
    "extract": {
        "src_ip": "src_ip",
        "srcip": "srcip",
        ... (many lines)
    },
    "map": {
        "srcip": "src_ip",
        "dstip": "dst_ip",
        ... (many lines)
    }
}

After (v2):

{
    "schema_version": 2
    // Remove "extract" section entirely
    // Remove "map" section entirely
    // Keep: detect, parsing, normalize, severity_mapping
}

That's it! The global PHF handles all field mapping automatically.

FAQ

Q: What if my vendor uses a completely unique field name?
A: Add it to src/unified_field_map.rs and rebuild. This benefits all future decoders.

Q: Can I still use explicit mapping for edge cases?
A: Yes. If your decoder has a map section, it will be used instead of the global PHF (legacy mode).

Q: How do I handle multi-format logs (some JSON, some KV)?
A: Create separate decoders with different detect patterns, or use regex patterns in parsing.patterns.

Q: What's the performance difference?
A: PHF is O(1) compile-time hash with zero collisions. The JSON-based KV parsing is ~6x faster than regex.
